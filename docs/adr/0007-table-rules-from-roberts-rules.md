# ADR 0007 — 卓のルールは Robert's Rules of Poker（Version 11）に従い、合法な行動の一覧・ポットの分け方・進み方を Core の 1 経路ずつにする

- 状態: 受理
- 日付: 2026-10-26
- Issue: #5
- 影響する規則: ARC-001 / ARC-004 / ARC-007 / ARC-010 / SWF-002 / QLT-008

## 文脈

ノーリミット・テキサスホールデムのルール（FR-02）は、店ごとの細かな違いがある。出典を 1 つ決め、その文書の番号でコードとテストを引けるようにする。
選んだのは **Robert's Rules of Poker, Version 11**（Robert Ciaffone 著）。著者の前書きは、ほとんどの規則が一般に使われていること、
誰でも写して使ってよいことを書いている（2026-10-26 に https://www.pagat.com/docs/RobsPkrRules11.pdf から取得して読んだ）。
このリポジトリが使う規則と、文書の中の場所:

| 規則 | 出典の場所 |
| --- | --- |
| 親（ボタン）は 1 ハンドごとに時計回りに 1 席動く。2 枚のブラインドは親の時計回りの 1 つ目がスモール、2 つ目がビッグ。プリフロップはブラインドの次の人から、それ以降は親の次の行動できる人から | 第 4 節 Button and Blind Use の前文 |
| 親は常に次の人へ動き、ブラインドはそれに合わせる（Moving button） | 第 4 節 Rules for using blinds の 2(a) |
| 2 人のときはスモールブラインドが親。2 人になったとき、いちばん最近ビッグブラインドを出した人が親になり、相手がビッグブラインド | 同 3 |
| ブラインドが足りなくても、最小の賭けとレイズの大きさはそのまま | 同 1 |
| レイズの回数に上限は無い | 第 14 節 No-limit rules の 1 |
| 最小のベットはビッグブラインド。最小のベットに足りないオールインに対してレイズするなら、少なくとも最小のベットを足す | 同 2 |
| レイズはそのストリートの直前のベットかレイズの幅以上（オールインは例外）。すでに行動して満額のレイズに向き合っていない人は、足りないオールインに対してレイズできない | 同 3 |
| 足りないオールインが重なり、その人から見て満額のレイズの幅に届けば、レイズの権利が開く | 同 4 |
| サイドポットとメインのポットは別々に分ける | 第 3 節 Ties の 5(d) |
| 同じ強さの手で分けて割り切れないチップは、親から時計回りで最初の手が受け取る。1 人が受け取る端数は 1 チップまで | 同 5(a)・4 |
| スートは引き分けを決めない | 同 1 |

## 決定

1. **席**: `Seat` は時計回りの 4 席（南・西・北・東）。名前は画面の配置と同じにしたが、Core にとって意味があるのは時計回りの順だけ
2. **行動**: `Action` は `fold` / `check` / `call` / `bet(合計)` / `raise(合計)` / `allIn` の閉じた enum。額は「そのストリートでいくらまで出すか」の合計で表す。
   **持っているチップを全部出す行動は、ベット・コール・レイズのどれに当たるときも `allIn` の 1 つ**で表す（全部に届くベット・レイズ・コールは `amountIsAllIn` / `callNotPossible` で拒む）
3. **合法な行動の一覧**: `Hand.legalActions`（`LegalActions`）が唯一の経路。`Hand.apply` も同じ一覧の `rejection(of:)` で確かめ、拒否は閉じた理由（`ActionRejection`）で返す。
   Engine はこの一覧から選ぶ（ARC-001）。チェックできるときの `fold` は一覧に入れない（AI だけが打つ卓で、意味の無い降りを出さない。ルールが禁じているからではない）
4. **レイズの権利**: 席ごとに「最後に行動したときの賭けの高さ」を持ち、いまの賭けとの差が直前の満額のレイズの幅以上なら開いている（第 14 節の 3・4 をこの 1 つの式で表す）。
   満額に届かないオールインは賭けの高さを上げるが、レイズの幅は変えない
5. **プリフロップの賭けの高さ**は、ビッグブラインドが足りなくてもビッグブラインドの額（第 4 節の 1）。ビッグブラインドはリンプされたらチェックかレイズを選べる
6. **進み方**: `Hand.progress` は「この席の行動を待つ」「場札を開くのを待つ（`dealNextStreet()`）」「終わった」の 3 つ。画面が場札を開く前に 1 間隔待てるように、場札を開くのは呼ぶ側の 1 手にした。
   行動できる人が 1 人だけで賭けに届いているなら誰も行動せず、場札を開いていくだけになる（全員オールイン）。バーンカードは置かない（配る順が乱数なので結果は変わらない）
7. **ポットの分け方**: `PotDivision.divide` が唯一の経路。出した額の段ごとに層を作り、その層まで出した降りていない席が争う。同じ顔ぶれの層はまとめる（メインと 2 つまでのサイド）。
   争う人が 1 人の層（コールされなかった分）はその人に戻る。端数は親の次の席から時計回りに 1 チップずつ
8. **卓**: `Table` は 4 席のチップ・親・ハンド番号・各席が最後にビッグブラインドを出したハンドを持つ。2 人になったときに、いちばん最近ビッグブラインドを出した人を親にする（第 4 節の 3）。
   その人がいない（2 人とも出したことが無い）ときは、時計回りに次のチップのある席
9. **ブラインドの段階**: `BlindSchedule` はビッグブラインドの並びと 1 段階のハンド数。スモールはビッグの半分。具体的な値と 1 段階のハンド数は、AI を入れた後に 1 卓の長さを計測して決める（Phase 3-5 の ADR）
10. チップの額は `Int` のまま持つ（下の却下した選択肢）

## 強制

- **active**: 行動・ストリート・席の状態・ハンドの終わり方は閉じた enum で、全捕捉は CNF-013 が拒む。テスト（`make test`）が次を見る:
  ブラインドと手番（4 人・ヘッズアップ）・ビッグブラインドのオプション・最小のベットとレイズ・全部のチップはオールイン・
  第 14 節の 3 の例（足りないオールインでレイズの権利が開かない）と 4（重なったオールインで開く）・足りないブラインド・
  1 つと 2 つのサイドポット・降りた人の分・端数（2 人・3 人のスプリット）・ショーダウンのスプリット・親の回り方とヘッズアップへの移り方・
  乱数で打った 200 卓の全行動で「手元のチップ＋場のチップ」が変わらない・同じ札が 2 度出ない・全卓が優勝で終わる・同じシードで同じ行動の列
- **planned**: 「Engine が合法な一覧から選ぶ」はレビュー事項（ARC-001）。Engine を入れる PR で「AI の行動は必ず合法」をテストにする

## 結果

- 卓のルールの疑問は、出典の節と番号で答えられる
- 失うもの: 店ごとに違う細則（デッドボタン・ハンドの途中の参加・時間の制限など）は扱わない。スクリーンセーバーの卓には現れない

## 却下した選択肢

| 選択肢 | 却下の理由 |
| --- | --- |
| 大会向けの規則集（TDA）を出典にする | 大会の運営の細則が多い。出典の著者自身が TDA とほぼ互換と書いており、卓の基本は同じ。1 冊にまとまった Robert's Rules を選んだ |
| 一般向けの百科事典のルールの記事を出典にする | 細則（足りないオールインの扱い・端数）の書き方が節ごとに揺れ、番号で引けない |
| デッドボタン（Robert's Rules の 2(b)） | 飛んだ席の前にボタンやブラインドが置かれ、画面で「誰が親か」が分かりにくくなる。2(a) の Moving button を選んだ |
| 全部のチップを出すベット・レイズを `bet` / `raise` でも書けるようにする | 同じ行動に 2 つの形ができる（ARC-001）。画面の `ALL-IN` も 1 つの形から出せる |
| チップの額を専用の型（`Chips`）にする | 額は足し引きと比べることにしか使わず、負にならないことはハンドの経路が守る（`put` の 1 か所）。型を作っても防げる誤りが増えない。SWF-001 は planned のレビュー事項なので、この判断をここに残す |
| 場札の公開を `apply` の中で自動で進める | 画面が「開く前に 1 間隔待つ」（画面仕様）を表すには、開く時を呼ぶ側が決める必要がある |
